# 聚合 API 冷却状态与手动重置

## Goal

让管理员在聚合 API 管理界面直接识别每个上游的实时冷却状态、剩余时间和触发原因，并能在确认风险后手动解除单个 API 的冷却，减少只能从请求日志推断路由行为的排障成本。

## Background

- 聚合 API 当前按运行时连续失败次数触发内存冷却；默认阈值为 5 次，冷却 5 分钟。
- 冷却状态按 `aggregate_api_id` 维护，不区分模型；进入冷却后，该 API 会从仍有健康候选的请求中被提前过滤。
- 当前请求日志只显示实际尝试链，未直接展示被冷却过滤的候选及剩余冷却时间。
- 用户希望在界面直接查看冷却状态并允许手动重置。

## Requirements

### R1. 冷却状态可见

- 聚合 API 列表应能区分 `正常` 与 `冷却中`。
- 冷却中应至少显示剩余时间和冷却原因。
- 状态应反映服务进程中的实时内存状态，而不是仅依据数据库历史推算。
- 冷却到期或被成功清除后，界面应及时恢复为正常状态。

### R2. 手动重置

- 管理员可针对单个聚合 API 手动解除冷却。
- 操作应明确说明解除后该 API 会立即重新进入路由候选。
- 重置操作必须通过现有 typed API/RPC/transport 链路完成，并保留服务端权限校验。
- 操作成功或失败均应有明确反馈，避免静默失败。

### R3. 兼容现有管理体验

- 功能应落在现有聚合 API 管理工作流内，不新增独立一级页面。
- 以现有高密度表格为基础，将第一列“供应商 / URL”收窄，把释放出的横向空间用于新增独立的“路由状态”列。
- “路由状态”应与现有用于启停配置的“状态”列明确区分；现有列在界面文案上可调整为“启用”，避免把运行时冷却误解为配置已禁用。
- 新列应放在 `Guard` 与“启用”之间，使运行时路由健康状态和配置启停状态相邻呈现。
- 视觉和交互应沿用当前桌面端/Web UI 的管理工具密度、glass theme、主题和低透明度模式。
- Desktop 与 service-mode Web UI 都应可用。

## Acceptance Criteria

- [ ] 冷却中的 API 在现有聚合 API 列表中具有清晰、可访问的状态标识。
- [ ] 第一列收窄后，供应商名和 URL 保持单行截断并可通过现有 Tooltip 查看完整内容，不明显增加表格行高。
- [ ] “路由状态”和“启用”具有不同的列标题与视觉语义，用户不会把冷却误认为手动停用。
- [ ] 用户无需打开请求日志即可看到剩余冷却时间和触发原因。
- [ ] 剩余时间会自动更新，冷却到期后状态自动恢复。
- [ ] 管理员可从列表上下文中解除单个 API 的冷却，并收到成功/失败反馈。
- [ ] 重置后下一次状态刷新显示该 API 已恢复为正常候选。
- [ ] 非冷却 API 不展示误导性的重置主操作。
- [ ] Desktop 与 service-mode Web UI 使用同一业务语义和 typed transport。
- [ ] 不暴露 API secret、鉴权参数或其他敏感配置。

## Out of Scope

- 本任务暂不调整连续失败阈值、冷却时长或失败分类算法。
- 本任务暂不提供批量解除全部冷却。
- 本任务暂不把内存冷却状态持久化到 SQLite。

## Open Questions

- 已决：冷却行显示失败进度（例如 `连续失败 5/5`）；最近错误摘要通过脱敏 Tooltip/Popover 展示。
- 已决：手动解除冷却必须经过确认弹窗；文案明确说明该 API 会立即重新进入路由候选。
