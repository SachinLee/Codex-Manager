# Codex Manager 桌面端资源评估执行计划

## 1. 执行约束

- **质量档案**：`lightweight`，因为本任务只收集证据并形成评估文档，不改变产品行为。后续任何代码候选必须进入独立批准的 `standard` 任务。
- **本轮允许修改**：仅任务级规划产物。不得修改 `apps/`、`crates/`、构建配置或默认设置。
- **本轮禁止执行**：不得启动 CodexManager，不运行格式化、lint、构建、测试或项目级验证；不得把当前无进程状态写成资源结论。
- **验收项引用**：按 `prd.md:27-32` 的顺序使用 AC-1（路径盘点）、AC-2（优先级清单）、AC-3（Windows 基线）、AC-4（不建议/证据不足）。
- **数据位置**：未来经用户批准的测量原始数据放在本任务 `research/measurements/<run-id>/` 下；只保存脱敏的环境清单、进程映射、计数器 CSV、场景事件与分析结果，不另建计划系统。

### Slice 2：AC-3 — 准备可复现 Windows 采集环境

此切片是后续经批准的只读运行步骤；本轮不执行。

- **行为**：在不触碰真实用户产品环境的前提下，产生可归属、可重复、可比较的 Windows 资源时间序列。
- **前置条件**：
  1. 使用固定的发布构建或已安装版本，不使用 Next.js 开发服务器、调试器、构建器或测试进程。
  2. 使用用户批准的独立 QA/便携配置和脱敏测试账号；禁止复制真实密钥。若没有隔离配置或获批的请求目标，停止，不启动或修改用户现有实例。
  3. 三次重复使用相同 Windows 构建、WebView2 Runtime 版本、显示器/缩放、网络、应用版本、页面、数据规模和电源模式；记录而不擅自更改用户默认电源或产品配置。
  4. 每轮开始前确认没有上一轮 CodexManager/Tauri/WebView2 实例；该确认只是防止样本混合，不是资源结论。
- **环境清单**：记录 UTC 时间、Windows 版本、CPU 型号/可用逻辑处理器（本机探测为 8）、物理内存（本机探测为 15.71 GiB）、WebView2 版本、应用版本/提交、显示缩放、电源模式、测试配置标识和设置快照。设置快照必须脱敏。
- **进程归属**：
  1. 在启动前、服务就绪后、每个场景结束时，用 `Get-CimInstance Win32_Process` 保存 `ProcessId`、`ParentProcessId`、`Name` 和已脱敏的 `CommandLine`。
  2. 从本轮 Tauri PID 递归关联 `msedgewebview2.exe` 后代；不要把机器上其他 WebView2 应用混入。
  3. 不寻找“桌面本地服务子进程”：源码表明服务在线程内运行。使用 WPR/WPA CPU Sampling（或等价 ETW）按线程名/调用栈区分 `http-worker-*`、`http-stream-worker-*`、后台任务和 UI 宿主 CPU。
- **计数器**：每秒采集一次 `\Process(*)\ID Process`、`\Process(*)\% Processor Time`、`\Process(*)\Private Bytes`、`\Process(*)\Working Set - Private`、`\Process(*)\Thread Count`；按 PID 而不是易冲突的实例名称关联。需要视觉路径归因时同时采集 WebView2 GPU Engine 利用率，但不把 GPU 指标替代 CPU/内存结论。
- **统一计算**：
  - 每场景报告宿主、WebView2 子进程及合计的 Private Bytes / Working Set - Private 的中位数、P95 和峰值。
  - CPU 保留总 CPU 时间增量；归一化 CPU% = `CPU 时间增量 / (墙钟时间 × 8) × 100`。若直接使用可超过 100% 的 Windows `% Processor Time`，先除以当轮记录的逻辑处理器数。
  - 启动峰值、稳定值和退出后的进程消失分别报告，不用单点任务管理器截图替代时间序列。
- **预期验证**：原始样本时间戳单调、无大段缺失；每个 PID 都能映射到本轮实例；三轮使用同一配置；计数器原始值与汇总公式可由另一执行者重算。
- **回滚**：结束经批准的隔离实例并删除临时 QA 配置；不写回用户配置。保留脱敏原始数据和失败原因。
- **停止条件**：发现 PID 混入、后台更新/杀毒扫描主导、采样丢失、版本或设置漂移时废弃该轮并重做；无法隔离用户环境时整个动态采集停止。

### Slice 3：AC-1 / AC-3 — 执行启动、空闲、活动请求场景

此切片同样只描述后续获批运行，不在本轮执行。

#### 3.1 启动场景

- **步骤**：从确认无旧实例开始采样，记录 T0 后启动固定发布构建；持续 90 秒，并记录 UI/服务首次显示“已连接”的时间点。完整退出，重复三次。
- **观察**：宿主/WebView2 进程出现顺序、线程数、Private Bytes/Working Set - Private 峰值、CPU 时间、服务就绪前后变化。
- **预期验证**：三轮都完成服务就绪；如某轮启动失败，则作为功能失败记录而不是从性能统计中静默删除。

#### 3.2 可见空闲与页面保活场景

- **步骤**：服务就绪后静置 2 分钟，再在固定首页可见状态采样 15 分钟；15 分钟窗口用于覆盖默认 60/180/600 秒后台周期。随后按固定顺序打开同一组顶级页面，每打开一页等待 60 秒，返回首页后再等待 5 分钟。重复三次。
- **观察**：后台周期 CPU 尖峰、访问页面数量与 WebView2 Private Bytes 的关系、返回后是否回落、隐藏页是否仍产生网络/RPC。聚合 API 页另作为“活动页面空闲”采样 5 分钟，标注其 1/2/5/15 秒更新节奏。
- **预期验证**：隐藏聚合页的查询应受活动状态门控；若仍有流量，先定位触发者，不能直接归咎于 keep-alive。

#### 3.3 托盘与视觉 A/B 场景

- **步骤**：从同一隔离配置副本派生单变量场景：视觉性能模式开/关；关闭到托盘且保留 UI/销毁 UI。每个状态稳定 2 分钟后采样 5 分钟，并记录重新打开窗口到可交互的时间及页面状态是否保留。
- **观察**：WebView2 进程是否退出、宿主服务是否继续、UI 私有内存差异、可见窗口 CPU/GPU、重开延迟和状态损失。
- **预期验证**：销毁 UI 后后台网关仍可用；视觉 A/B 使用同一页面与固定交互序列。只改变一个设置，结束后恢复配置副本。

#### 3.4 活跃网关请求场景

- **步骤**：使用批准的本地 mock/QA 上游和固定、无敏感信息的请求脚本；若不存在获批入口则停止。先固定聚合页面为非活动，排除其轮询。分别执行普通响应与流式响应，固定请求内容、响应字节数、持续时间和并发；至少完成并发 1 的场景，Worker 评估再增加受控并发阶梯。每个场景预热 1 分钟、采样 5 分钟、冷却 2 分钟，重复三次。
- **观察**：CPU 时间、Private Bytes、线程 CPU、吞吐、P50/P95/P99 延迟、错误率、普通/流式队列深度、入队失败和首次请求延迟。
- **预期验证**：请求数、成功数和响应内容符合脚本；资源数据与网关指标时间窗口一致；付费真实上游、真实密钥或不确定请求成本不允许作为默认实验路径。

#### 3.5 “代理测试后空闲”场景

- **步骤**：先测纯净启动空闲，再在同一隔离实例完成一次最小代理测试并等待任务结束，继续采样 5 分钟。
- **观察**：`proxy-jobs-scheduler` 是否持续以约 50 ms 周期唤醒，以及相对纯净空闲的 CPU 时间差。
- **预期验证**：只有首次使用后出现的差异才能归入 JobRegistry；未使用代理测试的用户不能获得该候选的启动收益声明。

- **本 Slice 回滚**：退出隔离实例，销毁 QA 配置副本；不改默认值。
- **本 Slice 停止条件**：请求结果、页面状态、服务连接或配置发生异常即停止该场景，先记录功能失败；不以异常低负载数据进入排序。

### Slice 4：AC-2 — 量化已有设置建议

- **行为**：优先判断无需代码修改的现有能力能否满足用户目标。
- **分析顺序**：
  1. 视觉性能模式：可见页面 CPU/GPU 与 WebView2 内存；记录视觉代价。
  2. 托盘销毁 UI：托盘空闲内存、后台服务可用性、重开延迟与状态损失。
  3. 已有 Worker 运行档位：在相同普通/流式负载下比较线程数、内存、吞吐、尾延迟和队列失败。
  4. 后台任务开关/间隔：仅对明确不需要对应功能的隔离配置 A/B；同时记录用量、保活、令牌新鲜度影响。
- **排序规则**：先按“可复现收益 × 置信度”，再按低实现成本和低回归风险；没有实测的项写“收益未测量”，不填推测区间。运行间差异必须超过同场景三次重复的波动，才能写为方向性结论。
- **预期验证**：每条建议包含适用运行形态、前置条件、测量窗口、原始数据引用、资源差异、体验/功能代价和恢复步骤。
- **依赖**：Slice 2、3 的有效三轮数据。
- **回滚**：恢复测量前设置快照。
- **停止条件**：设置收益不稳定、功能代价不可接受或只在开发环境出现时，不推广该建议。

### Slice 5：AC-2 / AC-4 — 形成候选排序与否决记录

- **行为**：输出最终评估矩阵，而不是直接实现候选。
- **矩阵列**：候选、源码锚点、触发路径、桌面/服务模式适用性、基线证据、收益值或不确定性、实现成本、并发/可靠性/UX 风险、验证 seam、回滚、停止条件。
- **决策规则**：
  1. 已有设置能取得同等结果时，不创建代码候选。
  2. 只有资源差异可重复且能归因，才把候选提升到后续任务。
  3. 所有 CPU/内存下降必须与吞吐、尾延迟、错误率、队列失败、新鲜度或重开体验共同评估。
  4. 缓存、线程栈、后台可靠性能力、WebView2 多进程/GPU 等缺乏证据的方向明确列为“不建议”或“证据不足”。
- **预期验证**：AC-1 至 AC-4 各能追溯到至少一份源码或动态证据；任何无动态数据的候选都显式标为假设。
- **依赖**：Slice 1；有动态结论时还依赖 Slice 2-4。
- **回滚**：若发现样本污染或计算错误，撤回受影响排序并从原始数据重算，不用文字补丁掩盖数据问题。
- **停止条件**：无法区分噪声与效果时，以“无结论”结束，不强行给出节省区间。

## 4. 条件式后续代码切片（本任务不执行）

只有 Slice 5 提升的候选才进入新的 `standard` Trellis 任务；每次只实现一个候选并保留相同 Windows 基线作 GREEN 之后的行为验证。

### Follow-up A：JobRegistry 事件驱动调度

- **Gate**：代理测试后空闲 CPU/唤醒可重复归因于 50 ms 循环。
- **代码 seam**：`JobRegistry` 的创建、排队、取消接口；调用者不感知调度器实现。
- **RED**：并发行为测试证明无任务时不周期扫描，任务入队能及时唤醒，取消与并发上限保持既有语义。
- **实现**：用通知/通道驱动调度，删除永久 50 ms 空轮询，不新增第二套调度路径。
- **GREEN/验证**：目标 Rust 测试、代理延迟/速度任务集成场景，以及 Slice 3.5 的同机 A/B；比较任务启动延迟、取消、错误率和空闲 CPU。
- **回滚**：整体恢复原调度实现；不保留兼容开关。

### Follow-up B：HTTP Worker 档位或延迟创建

- **Gate**：现有较低 Worker 配置稳定降低目标资源，且在既定普通/流式负载下没有越过吞吐、尾延迟和队列失败界限。
- **代码 seam**：`http_worker_count` / `http_stream_worker_count` 与 Worker/队列启动策略（`crates/service/src/http/backend_runtime.rs`）。
- **RED**：覆盖 8 逻辑处理器的桌面档位、最小/最大值、有界队列，以及普通与流式隔离的行为测试。
- **实现**：优先调整已有档位/推荐逻辑；只有首次请求证据支持时才做延迟创建。不得暴露线程管理给路由调用者。
- **GREEN/验证**：目标 Worker/队列测试、普通/流式负载、首次请求延迟、队列深度/失败和 Slice 3.1/3.4 A/B。
- **回滚**：清晰恢复既有计算与默认档位；不保留双默认。

### Follow-up C：页面保活上限

- **Gate**：访问页面数量与 WebView2 私有内存有可重复增长，且低资源托盘模式不能覆盖可见窗口使用场景。
- **代码 seam**：`PageKeepAliveViewport` 的驻留策略。
- **RED**：通过顶级导航行为验证活动页永不驱逐、上限可预测、驱逐后返回能正确重载；对要求保存草稿的页面验证退出提示或状态策略。
- **实现**：最小 LRU/明确页面策略，删除无界驻留；不让每个页面自行实现第二套缓存协议。
- **GREEN/验证**：导航行为测试、页面状态/请求次数、固定页面序列的堆/Private Bytes A/B 与重开延迟。
- **回滚**：恢复当前全保活策略；若状态丢失或重复副作用出现立即回滚。

### Follow-up D：聚合 API 刷新收敛

- **Gate**：活动页 1/2/5/15 秒更新可归因地贡献目标 CPU/RPC，且产品可接受明确的新鲜度界限。
- **代码 seam**：聚合状态查询 hook 的刷新接口。
- **RED**：网络层行为测试覆盖活动/隐藏切换、刷新节奏、窗口后台和重新激活后的即时刷新。
- **实现**：共享快照、合并重复查询或调整间隔；保留活动状态门控，不添加新的全局轮询器。
- **GREEN/验证**：请求节奏、数据新鲜度、错误恢复和 Slice 3.2 的活动页面 A/B。
- **回滚**：整体恢复原刷新策略。

### Follow-up E：后台调度与缓存

- **Gate**：ETW/长时曲线分别证明某个后台调度器或缓存是主因；“存在一个线程/HashMap”不满足 Gate。
- **代码 seam**：对应后台任务设置/唤醒接口，或网关候选客户端获取/失效接口。
- **RED**：调度重配、关闭、错误退避、关闭流程或缓存容量/失效/连接复用契约的行为测试。
- **实现**：只改已归因模块；不得一次合并全部调度器或无差别清缓存。
- **GREEN/验证**：目标行为测试、15 分钟空闲或长时多账号请求 A/B，并同时验证用量/令牌/健康新鲜度或连接建立延迟。
- **回滚**：恢复单一既有实现和上限；任何可靠性或延迟反向退化即停止。
