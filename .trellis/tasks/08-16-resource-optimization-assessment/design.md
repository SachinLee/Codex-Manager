# Codex Manager 桌面端资源评估设计

## 1. 设计状态与质量档案

- **任务性质**：只读评估与后续方案设计，不修改产品代码、构建配置或默认设置。
- **质量档案**：`lightweight`。理由是本任务只写 Trellis 规划文档并设计可复现实验，不改变运行时行为、持久化数据或公开契约；尽管如此，任务要求的 `design.md` 与 `implement.md` 仍完整保留。任何后续并发、调度或页面生命周期改动必须另建或重新批准为 `standard` 行为变更任务。
- **需求真相**：以 `prd.md` 为准。本文按 PRD 中验收项出现顺序简称 AC-1 至 AC-4（`prd.md:27-32`），不改写其范围决定。
- **证据边界**：本机有 8 个可用逻辑处理器、15.71 GiB 物理内存，但当前没有 CodexManager 进程。本任务没有启动产品，也没有任何可归因的 MB、CPU%、耗电或收益实测；“无进程”仅表示当前无法取样，不是性能结论。

## 2. 评估边界与资源归属

桌面端是主评估对象。Tauri 主进程在同一进程内启动 Rust 本地服务线程，而不是再派生一个独立服务进程（`apps/src-tauri/src/service_runtime.rs:58-88`）；WebView2 的渲染、GPU、网络等子进程需要和 Tauri 主进程一起按进程树聚合。因而：

- 进程级内存可以区分 Tauri/Rust 宿主与 WebView2 子进程，但不能仅凭进程私有内存继续拆分“Tauri 框架”和“Rust 服务”；这类归因需要线程 CPU/ETW 栈或受控 A/B。
- 桌面端总量必须同时报告宿主进程与所有归属到该实例的 WebView2 子进程，不能只观察任务管理器中的一个名称。
- 服务模式只记录边界差异：它没有 Tauri 窗口、WebView2、页面保活、视觉效果与托盘生命周期；Rust 服务启动任务、HTTP Worker、网关请求和服务端缓存仍适用。服务模式不单独建立本轮基线。

评估使用两个互补的内存指标：`Private Bytes` 表示进程提交的私有地址空间，`Working Set - Private` 表示当时驻留的私有页。二者都按归属进程树汇总；不能把 512 KiB 线程栈配置直接当作等量常驻内存。CPU 同时保留累计 CPU 时间斜率与按 8 个逻辑处理器归一化后的百分比，避免 Windows 计数器可超过 100% 所造成的歧义。

## 3. 分级资源路径

### 3.1 启动路径

1. `AppBootstrap` 读取设置后，在桌面运行时启动并初始化本地服务；桌面壳先可用，服务连接异步完成（`apps/src/components/layout/app-bootstrap.tsx:279-318`）。
2. Tauri 命令会停止旧运行时、检查监听地址、在宿主进程内启动服务并等待就绪（`apps/src-tauri/src/commands/service.rs:109-141`；`apps/src-tauri/src/service_runtime.rs:58-88`）。
3. 服务入口初始化存储与运行设置，然后依次确保用量轮询、网关保活、令牌刷新、预热 cron、聚合健康检查和插件调度器，再启动 HTTP 服务（`crates/service/src/lifecycle/startup.rs:69-82`）。这些入口在启动时被调用，不等于每项都在持续执行有效工作。
4. 默认后台设置为用量轮询 600 秒、网关保活 180 秒、令牌刷新 60 秒且均启用，预热 cron 关闭（`apps/src/lib/api/normalize.ts:82-96`）。
5. HTTP 后端按可用处理器计算两组常驻 Worker。当前机器 8 个逻辑处理器对应普通 Worker 上限 16、流式 Worker 上限 4；每个线程显式配置 512 KiB 栈（`crates/service/src/http/backend_runtime.rs:12-22,52-82,153-170`），并在服务启动时创建两组有界队列和 Worker（`crates/service/src/http/backend_runtime.rs:353-362`）。20 × 512 KiB 只能作为栈保留规模的源码事实，不能声称产生 10 MiB 常驻集。

**启动风险假设**：Worker 数量、WebView2 进程初始化和多个后台运行时可能贡献启动峰值；需要启动时间序列和线程级证据后才能排序。单看源码线程数不能推出 CPU 或内存收益。

### 3.2 空闲路径

1. **后台任务**：默认轮询间隔较长，功能上承担用量新鲜度、网关可用性和令牌有效性。设置页已经允许启停及调整间隔（`apps/src/app/settings/components/tasks-tab-content.tsx:84-174`）。长间隔线程可能主要处于休眠，因此仅凭“线程存在”不判定为高 CPU。
2. **聚合健康检查与插件调度**：启动入口始终确保调度器存在；聚合健康检查自身限制每日探测并按已启用配置执行（`crates/service/src/aggregate_api_health.rs:700-739`）。禁用或延长它会改变故障发现时间，不能作为无风险优化。
3. **代理测试 JobRegistry**：全局注册表首次使用时才创建单 Worker Tokio 运行时和调度循环（`crates/service/src/account/proxy_testing/jobs.rs:154-170,604-615`）；一旦创建，调度器即使没有任务也每 50 ms 唤醒并扫描（`crates/service/src/account/proxy_testing/jobs.rs:717-736`）。它不属于纯净启动空闲路径，但属于“执行过一次代理测试后的空闲路径”。
4. **页面保活**：所有已打开顶级页面都保持挂载，仅用 `hidden` 隐藏非活动页面（`apps/src/components/layout/page-keep-alive-viewport.tsx:173-195`），因此 DOM、React 状态和查询缓存可能随访问页面数量增长。聚合 API 页面已按活动页面门控查询（`apps/src/app/aggregate-api/page.tsx:179-188`），所以“保持挂载”不等于所有页面持续轮询。
5. **活动页面轮询**：聚合 API 页面活动时，运行状态与零余额状态每 2 秒刷新，其中运行状态还每秒更新倒计时（`apps/src/hooks/useAggregateApiRuntimeStatuses.ts:8-24`；`apps/src/hooks/useAggregateApiZeroBalanceStatuses.ts:8-17`）；同页健康状态 15 秒、两组用量统计 5 秒刷新（`apps/src/app/aggregate-api/page.tsx:228-289`）。这是“活动页面空闲”而非后台隐藏页面的负载。
6. **视觉渲染**：已有“视觉性能模式”开关（`apps/src/app/settings/components/general-basics-card.tsx:204-212`），其低透明度样式关闭背景图、毛玻璃与阴影（`apps/src/app/globals.css:1193-1231`）。它优先用于验证 WebView2/GPU 合成相关占用，不需要产品改动。
7. **托盘生命周期**：Windows 已支持关闭到托盘后不保留窗口 UI；设置页明确说明“保留界面”与“销毁后重载”的取舍（`apps/src/app/settings/components/general-basics-card.tsx:172-202`）。运行态根据 `closeToTrayOnClose` 和 `keepWindowUiMounted` 计算轻量模式（`apps/src-tauri/src/commands/settings/tray_state.rs:68-106`），窗口销毁时保留后台服务（`apps/src-tauri/src/app_shell/lifecycle.rs:175-220`）。
8. **服务缓存**：网关候选客户端缓存有 512 条容量保护，达到上限会清空，并在运行配置刷新时清空（`crates/service/src/gateway/core/runtime_config.rs:120-121,616-691,2316-2330`）。在没有长时增长曲线和对象归因前，不把“删除缓存”列为优先项。

### 3.3 活跃请求路径

1. 普通请求与流式请求进入不同的有界队列和 Worker 组；满队列通过超时/失败形成背压，而不是无限堆积（`crates/service/src/http/backend_runtime.rs:84-117,333-375`）。
2. 网关已有总请求、活动请求、普通/流式队列容量与深度、入队失败、上游耗时和错误计数（`crates/service/src/gateway/observability/metrics.rs:9-42,58-94`）。后续负载评估应将这些可靠性/吞吐指标与 CPU、内存同时读取，不能只追求更少线程。
3. 候选上游客户端会按账号、聚合 API 和代理配置复用；降低缓存可能减少保留内存，也可能增加连接建立、TLS 与代理初始化 CPU/延迟（`crates/service/src/gateway/core/runtime_config.rs:616-691`）。
4. 活跃聚合 API 页面同时触发 2 秒、5 秒和 15 秒查询，因此请求负载实验必须固定当前页面，避免把管理页面轮询混入网关请求 CPU。

## 4. 优化候选分层

### 4.1 已有可配置缓解措施（当前可给用户的建议）

这些建议仅改变用户主动选择的运行模式，不是本任务的代码改动，也不能预先声称收益数值。

| 顺序 | 措施 | 适用资源路径 | 预期方向与不确定性 | 功能/体验风险 |
| --- | --- | --- | --- | --- |
| U1 | 开启视觉性能模式 | 可见窗口、页面切换与滚动 | 可能降低 WebView2 合成/GPU 相关活动；对 Rust 宿主内存未必有影响 | 失去毛玻璃、阴影等视觉效果 |
| U2 | 开启关闭到托盘，并关闭“窗口界面资源常驻” | 托盘空闲 | 销毁 WebView 后应降低 UI 相关驻留；具体幅度必须 A/B 测量 | 重开需重新加载，短期页面状态不保留；后台服务仍运行 |
| U3 | 先使用已有运行模式/高级 Worker 参数，而非改默认值 | 启动、活跃请求 | 较少 Worker 可能降低线程与栈保留；实际工作集收益和吞吐代价未知 | 并发、流式请求容量和队列等待可能退化（`apps/src/app/settings/components/tasks-tab-content.tsx:208-325`） |
| U4 | 仅在用户明确不需要相应功能时关闭轮询/保活/令牌刷新或延长间隔 | 服务空闲 | 可能减少定时唤醒和网络工作；默认间隔较长，CPU 收益可能低于噪声 | 用量陈旧、网关恢复变慢、令牌过期；不能作为通用默认建议 |

### 4.2 需要后续产品改动的候选项

以下均为**条件候选**，只有 `implement.md` 的基线与停止条件通过后才进入独立标准档案任务。

| 优先级 | 候选 | 触发证据 | 最小正确 seam | 收益不确定性 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| P1 | 将 JobRegistry 的 50 ms 扫描改为任务到达通知/有任务才调度 | “首次代理测试后空闲”出现稳定唤醒或可归因 CPU，且纯净启动空闲没有同样现象 | `JobRegistry` 创建/排队接口；调用者不学习调度细节 | 对从未使用代理测试的启动为零；对使用后空闲可能明显 | 通知丢失、任务饥饿、取消竞态、并发上限破坏 |
| P1 | 桌面档位自适应或延迟创建普通/流式 Worker | 宿主线程/私有字节在低并发时可归因于 16+4 Worker，且现有低资源档位 A/B 有稳定收益 | HTTP 运行时的 Worker/队列配置接口 | 栈配置不等于工作集，内存收益可能小；活跃负载才暴露代价 | 吞吐下降、流式饥饿、队列失败、启动后首次请求抖动 |
| P2 | 顶级页面保活改为有界 LRU/按页面策略卸载 | 已访问页面数与 WebView2 私有内存呈可重复单调增长，返回后不回落 | `PageKeepAliveViewport` 的页面驻留策略；页面只看到挂载/卸载语义 | 取决于用户访问路径和页面体积 | 表单/滚动状态丢失、重复请求、导航变慢 |
| P2 | 合并或放慢聚合 API 活动页 1/2/5/15 秒刷新 | 固定页面时 WebView2/RPC CPU 可归因，且数据新鲜度允许 | 聚合状态查询 hook 的刷新策略；页面消费统一快照 | 仅影响该页面活动时；隐藏页已门控 | 状态、余额或用量显示变陈旧，故障反馈变慢 |
| P3 | 后台调度器按启用状态延迟启动，或共享可唤醒计时器 | 线程级追踪显示长间隔调度器仍贡献可观 CPU/提交内存 | 背景任务设置/唤醒接口，保留每项任务的独立错误语义 | 休眠线程常常成本很低，可能无可见收益 | 时间漂移、重配不生效、关闭不及时、可靠性回归 |
| P3 | 调整网关客户端缓存淘汰策略 | 长时、多账号/代理场景证明缓存是保留内存主因 | 候选客户端获取/失效接口 | 当前已有 512 条上限和刷新清理，收益证据不足 | TLS/连接复用变差，CPU和请求延迟上升 |

深模块约束：后续实现应把调度、驻留或刷新策略藏在上述既有 seam 内，不向调用者暴露新的计时器、线程或缓存管理方法。只有确有第二种运行策略时才新增 Adapter；不得为评估结果创建传递型封装。

### 4.3 证据不足或不建议项

- 不根据当前“没有进程”的快照声称 Codex Manager 空闲资源为零或已经优化。
- 不把 20 个 512 KiB 栈直接换算成 10 MiB RSS，也不在无栈溢出和工作集证据时优先缩小线程栈。
- 不默认关闭令牌刷新、网关保活、聚合健康检查、插件调度或预热相关可靠性能力；预热本身默认已关闭。
- 不禁用 WebView2 多进程、GPU 或安全沙箱来换取未经验证的进程数量下降；这会引入稳定性、安全和渲染风险。
- 不把前端包体大小、构建耗时或依赖数量直接当作运行时内存证据；只有加载/堆快照证明某模块常驻时才进入候选。
- 不无差别清空网关缓存或缩短连接池寿命；当前缓存已有容量保护，连接复用损失可能反向增加 CPU 与延迟。
- 不把服务模式结果外推到桌面总量；服务模式缺少 WebView2、视觉与托盘生命周期。

## 5. 方案风险、回滚与停止条件

所有后续候选都采用“单变量、可关闭、先测后改”策略：保持相同构建、数据集、页面、请求脚本和 Windows 电源状态，只改变一个设置或一项实现。配置建议通过恢复测量前的设置快照回滚；代码候选通过恢复既有策略实现和默认值回滚，不保留双路径兼容层。

出现以下任一情况即停止推进相应候选并记录为“无结论”或“不建议”：

1. 三次重复的差异落在运行间波动范围内，无法稳定复现或无法归因到目标进程/线程。
2. 需要修改真实用户产品环境、读取未脱敏密钥或使用未经授权的付费上游才能完成测量。
3. 资源下降伴随请求失败、队列入队失败、令牌/用量陈旧、健康检查漏报、页面状态丢失或重开异常。
4. 活跃请求吞吐、尾延迟或首次请求延迟越过项目已有验收界限；若项目没有相关界限，先建立界限，不以主观“可接受”批准改动。
5. 只能在开发服务器、调试器或构建进程中观察到差异，无法在同一发布构建和相同 WebView2 版本中复现。
6. 优化需要新增常驻线程、轮询器、缓存层或公共设置，却没有比现有配置/能力更高的可验证收益。

本设计无迁移、发布或安全数据改动。基线原始数据应脱敏并保留在任务研究目录；任何包含命令行密钥、账号标识、请求正文或用户路径的字段不得进入持久化评估产物。
