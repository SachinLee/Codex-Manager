# 缓存率分析完成总结

## 已确认的根因

### 1. 数据验证了假设

**观测**: 用户报告的 66% 缓存率有日志依据
- 10:59 前的当日累计: **65.60%**
- 当前累计（12:23）: **71.76%**
- 滚动 24 小时: **88.13%**

**核心发现**:
- 29.83% 请求经历 Aggregate API 故障切换，缓存率仅 **51.71%**
- 单次成功请求缓存率: **81.18%**
- 会话内来源稳定请求: **78.58%**
- 会话内来源切换请求: **33.77%**

### 2. 技术根因

**R1 - Aggregate API 无会话亲和性**
- 所有请求走 `actual_source_kind=aggregate_api`, `route_source=route_strategy`
- `conversation_bindings` 表为空（现有绑定仅支持 Account 候选）
- `session_id` 被记录但不影响 Aggregate API 选择

**R2 - 故障切换破坏缓存池**
- 09:00-10:59 故障高峰期，65% 请求发生切换
- 不同 Aggregate API 使用独立上游账户 → 缓存隔离
- 21 次会话内成功切换，缓存率从 78.58% 降至 33.77%

**R3 - 失效候选制造无效跳转**
- `sort=105` 在 35 次尝试中最终成功 0 次
- 仍在 active 链中，制造额外延迟和缓存池切换

### 3. 故障分类（当日 trace log）

| 故障类型 | 次数 | 主要来源 |
|---|---:|---|
| rate_limit_exceeded | 9 | esfaery, ai.input.im |
| 上游临时不可用 | 4 | esfaery, wegoo |
| Cloudflare 验证/502 | 3 | timicc |
| 传输故障/超时 | 2 | esfaery, timicc |
| 响应写入失败 | 1 | esfaery |

## 建议的修复方案

**已采纳**: 会话级 Aggregate API 来源亲和性（默认关闭）

### 核心机制
1. 使用现有 cache-affinity route ID 查找上次成功的 Aggregate API
2. 若该来源仍可用，移到候选链首位
3. 失败时走现有 failover，成功后更新绑定到新来源
4. 保持冷却、余额、能力过滤优先级

### 预期改善
- 机械上界：将"来源切换"请求恢复到稳定会话水平 → **77.3%**（+5.5个百分点）
- 最佳情况：所有 failover 请求达到单次成功水平 → **81.18%**
- 实际取决于上游缓存实现和故障持续时间

### 立即可做（无需代码）
检查并临时停用 `sort=105`，观察切换占比是否从 29.83% 降至低个位数。
