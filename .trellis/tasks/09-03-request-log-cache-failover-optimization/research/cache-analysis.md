# 请求日志缓存率与故障切换分析

> 分析快照：2026-09-03 12:23 UTC+08:00。数据来自正在运行的 Codex Manager 的 SQLite 请求日志，辅以 `gateway-trace.log` 的最终失败事件。上游以其 Aggregate API 的 `sort` 值标识，避免把凭据或完整端点写入研究文件。

## 范围与方法

- 样本：当日 `gpt-5.6-terra` 成功请求；`request_logs` 与 `request_token_stats` 以 `request_log_id` 关联，并限定 `usage_included = 1`。
- 缓存率：`SUM(cached_input_tokens) / SUM(input_tokens)`。
- 故障切换：`json_array_length(attempted_aggregate_api_ids_json) > 1`。
- 会话切换：同一 `session_id` 的相邻成功请求，其 `actual_source_id` 不同。
- 说明：请求日志只持久化最终结果；它能证明候选链和最终成功来源，但不会保存同一条成功请求中每个失败候选的精确错误文本。错误类型来自同一时段 `gateway-trace.log` 的最终失败事件，不能按单条成功请求归因。

## 结果

### 1. 用户观测的 66% 有日志依据

| 时间范围 | 成功请求 | 输入 token | 缓存输入 token | 缓存率 |
|---|---:|---:|---:|---:|
| 08:00–09:59 | 86 | 7,988,979 | 5,172,256 | **64.74%** |
| 08:00–10:59 | 126 | 12,374,880 | 8,117,850 | **65.60%** |
| 当日快照（12:23） | 181 | 19,290,889 | 13,842,266 | **71.76%** |
| 滚动 24 小时 | 583 | 98,623,975 | 86,918,682 | **88.13%** |

因此，“今天综合约 66%”不是显示误差：在 10:59 前的当日累计值正是 65.60%。11:00 后故障切换显著减少，累计缓存率才回升至 71.76%。

### 2. 缓存下降与故障切换强相关

| 最终成功请求分类 | 请求数 | 占比 | 平均输入 token | 缓存率 |
|---|---:|---:|---:|---:|
| 单次候选成功 | 127 | 70.17% | 103,327 | **81.18%** |
| 经至少一次 Aggregate API 切换 | 54 | 29.83% | 114,228 | **51.71%** |

切换请求的平均输入仅比单次成功请求高约 10.6%，但缓存率低 **29.47 个百分点**。这是足以解释当日缓存率下降的主要相关因素。

按尝试次数进一步分组：

| 尝试次数 | 请求数 | 缓存率 | 最终来源不同于首选来源 |
|---|---:|---:|---:|
| 1 | 127 | 81.18% | 0 |
| 2 | 17 | 46.11% | 17 |
| 3 | 25 | 69.46% | 25 |
| 4 | 12 | **30.30%** | 12 |

所有多尝试请求都最终落在首选来源之外；四次尝试组的缓存率最低。一次切换不必然清零缓存，但每增加一个候选池就增加一次冷缓存或不同缓存策略的概率。

### 3. 会话内上游不稳定直接对应低缓存

当日 198 条 GPT 请求都有 `session_id`，但只有 181 条具备可计费 token 统计；其中只有 **5 个会话**，请求高度集中。`conversation_bindings` 表中记录数为 **0**，且 181 条有 token 的请求都记录为：

```text
route_strategy = ordered
route_source   = route_strategy
actual_source_kind = aggregate_api
```

会话相邻请求比较：

| 会话内来源状态 | 请求数 | 输入 token | 缓存率 |
|---|---:|---:|---:|
| 会话首个观测请求 | 5 | 322,813 | 2.02% |
| 与前一请求使用同一来源 | 155 | 16,580,006 | **78.58%** |
| 与前一请求来源改变 | 21 | 2,388,070 | **33.77%** |

同一会话切换来源后，缓存率比保持同一来源低 **44.81 个百分点**。相邻请求的平均输入规模相近（来源稳定约 107k，来源改变约 114k），不能用“切换请求提示词显著更短”解释这一差异。

> 这是当前数据中最强的直接证据：不只是单次请求的候选失败，成功会话在后续请求中也没有保持 Aggregate API 来源。

### 5. 候选池内存在一个零成功的中间候选

以下“最终成功率”表示该候选出现在尝试链某位置后，最终是否由它完成请求；它不是独立探测成功率。

| Candidate `sort` | 出现位置 | 被尝试次数 | 最终由该候选成功 | 最终成功率 |
|---:|---:|---:|---:|---:|
| 104 | 第 1 位 | 57 | 23 | 40.4% |
| 105 | 第 1/2 位合计 | 35 | **0** | **0.0%** |
| 205 | 第 1 位 | 107 | 92 | 86.0% |
| 205 | 第 3 位 | 32 | 22 | 68.8% |
| 350 | 各位置合计 | 27 | 20 | 74.1% |
| 400 | 各位置合计 | 22 | 22 | 100.0% |

其中 `sort=105` 在所有 35 次进入候选链时都未完成最终请求，却经常位于 `104 → 105 → 205` 路径中。它是额外增加一次无效尝试和一次缓存池转换的明确配置问题。`sort=400` 虽在本时段的最终成功记录中完成了 22 次请求，但当前健康探测状态为 failed；不应仅根据历史最终成功率将其提到主路径。

按最终成功来源的缓存率也呈现明显方差：

| 最终 Candidate `sort` | 请求数 | 作为切换后最终来源数 | 缓存率 |
|---:|---:|---:|---:|
| 104 | 23 | 0 | 82.69% |
| 205 | 116 | 24 | 81.47% |
| 350 | 20 | 10 | 52.42% |
| 400 | 22 | 20 | 40.72% |

低缓存来源主要是故障切换的落点，而非稳态主来源。

## 根因

### R1 — Aggregate API 路径没有会话亲和性

请求全都走 `actual_source_kind = aggregate_api`，所有日志为 `route_source = route_strategy`，而不是 `conversation_binding`。现有 `conversation_binding` 的候选类型是 `(Account, Token)`；Aggregate API 的候选循环在 `gateway/upstream/protocol/aggregate_api.rs` 中独立运行，并且没有等价的“会话 → Aggregate API”绑定。因此，客户端携带的 `session_id` 只被记录到日志，不能稳定选择同一个 Aggregate API。

这解释了为何已有 5 个长会话仍发生 21 次成功请求之间的来源切换。

### R2 — 故障切换把同一长上下文送入不同上游缓存池

`Aggregate API` 候选按 `ordered` 运行。上游的限流、不可用、Cloudflare 验证和超时使系统在一次请求内走过多个候选；成功后也不形成 Aggregate API 级别的会话绑定。不同 Aggregate API 实际使用独立供应商/账户路径，因此没有理由预期其 prompt cache 共享。

证据是：同会话来源稳定 78.58%，切换后仅 33.77%；多尝试请求仅 51.71%。

### R3 — `sort=105` 的零成功候选制造无效跳转

该候选在当日 35 次进入尝试链、最终成功为零，却留在 active 顺序链中。这不是“健康失败时偶尔换源”的必要成本，而是稳定地多加一跳。它放大延迟、故障窗口内的缓存损失和下游冷启动概率。

## 结论

是。频繁切换会显著降低当前环境的缓存率；本次不是 `balanced` 轮询导致，而是：

1. `ordered` Aggregate API 故障转移；
2. 上游在 09:00–10:59 发生限流、不可用、Cloudflare 验证和超时；
3. Aggregate API 层没有会话亲和性；
4. 顺序链中的 `sort=105` 候选在样本中 35 次零最终成功，造成额外跳转。

在不改变上游能力的情况下，把“来源改变”请求恢复到当前稳定会话的缓存率，按当日样本的机械上界可将 71.76% 提升到约 **77.3%**（+5.5 个百分点）。把所有故障转移请求恢复到单次成功组的缓存率是 **81.18%** 的上界，不是承诺；实际提升取决于上游是否共享缓存、故障持续时间和提示词前缀稳定性。

## 建议的行动顺序

1. **立即运维动作，不需要代码改动**：检查并停用/修复 Candidate `sort=105`；它没有在 35 次尝试中完成一次最终请求。不要据此自动提升 `sort=400`，因为其最新健康探测失败。
2. **恢复健康后复测**：通过同一查询观察 `attempt_count > 1` 占比是否从 29.83% 降至低个位数；这应先把缓存率带回约 80% 附近。
3. **产品实现方向**：为 Aggregate API 增加与现有账号绑定相同语义的、按 `key_hash + protocol + model + cache-affinity route ID` 分区的会话来源绑定；绑定来源冷却或不可用时才临时 failover，成功后更新绑定。
4. **不要实施跨账号/跨供应商统一 `prompt_cache_key` 实验**：这无法绕过独立上游账户的缓存隔离，且 OpenAI 没有承诺这一行为。应先完成来源稳定性和候选健康修复。
5. **增强可观测性**：把每次候选失败原因、候选位置、最终来源、是否破坏会话绑定写入请求日志；现有最终请求日志无法对成功 failover 的每一步精确归因。
