# 分析 OMP 会话执行时长

## Goal

定位 OMP 每个会话执行时间长的真实耗时来源，区分启动开销、上下文装载、模型等待、工具执行、子代理等待和收尾写入，并给出按收益排序的优化建议。

## Background

- 用户观察到 OMP 每个会话执行时间较长，当前尚未确定是 OMP 本身、项目级初始化、工具链、模型路由还是任务复杂度造成。
- 本次先做只读证据调查，不修改产品代码或 OMP 配置。

## Requirements

1. 检查 OMP 会话生命周期与启动/收尾链路。
2. 检查 hooks、skills、MCP、子代理和项目上下文是否引入固定或重复耗时。
3. 读取可用的运行时会话记录与时间字段，建立耗时分段证据。
4. 将观察到的事实、合理推断和无法确认的部分分开。
5. 给出无需改代码即可验证的诊断命令，以及按优先级排序的改进建议。

- `C:/Users/shuan/.omp/agent/config.yml` 使用 `codex-manager/gpt-5.6-terra:high` 作为默认模型；重试开启，最多 2 次并允许模型回退。
- `C:/Users/shuan/.omp/agent/agent.db:model_perf` 的历史均值：Terra TTFT 约 16.84 秒，Sol TTFT 约 31.60 秒，标题生成使用的 DeepSeek Flash TTFT 约 41.86 秒、平均生成耗时约 48.80 秒。
- PID 13412 的冷启动从 10:36:06.406 到 10:36:28.838 约 22.43 秒；期间出现供应商发现超时、Postman 401、OpenAI Developer Docs 403、IDA Pro 连接失败、Codex transport closed，以及 `context7` / `Context7` 工具冲突。
- 同一标题生成 session 在 10:39:17、10:40:21、10:41:46、10:45:39 重试四次，均 502；单次请求约 19.9–72.3 秒。AutoQA push 也多次返回 400。
- 复杂任务启动的 review 子代理准备耗时约 0.36–1.12 秒，但子代理工作本身会持续更久；PID 18652 同时运行 5 个 review 子代理并在 09:18–09:20 才陆续退出。
- `ui.loop-blocked` 最高观察到 5.259 秒和 6.084 秒；这是本地界面卡顿证据，但当前无法证明其占总时长的主要比例。

## Root Cause Ranking

1. P0：默认模型和标题模型的网络/模型等待；DeepSeek 标题链路明显慢且失败重试。
2. P0：每次启动加载失效 MCP 与重复 Context7，冷启动固定增加约 10–22 秒，故障时可达 30 秒级超时。
3. P1：复杂任务的多子代理与工具调用总量，放大完整会话墙钟时间。
4. P1：AutoQA 失败与 UI event loop blocked，造成后台噪声和尾部卡顿；需要 A/B 关闭验证。
