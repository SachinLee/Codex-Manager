# 聚合模型快捷路由

## Goal

管理员在聚合 API 的上游模型发现结果中，可将某一已发现模型快捷纳入本地“模型与路由”目录：建立或复用本地模型，并把该模型显式路由到发现它的聚合 API 与对应上游模型名，避免再次手工填写同一信息。

## Confirmed Facts

- 上游模型发现已完成并上线：`AggregateApiModelDiscoveryDialog` 位于聚合 API 页面，按 `apiId` 展示瞬时结果；RPC 只读调用上游 `/models`，不会落库。
- 本地模型目录 V2 与网关路由的唯一写入路径是 `ManagedModelV2Upsert`；路由字段为 `sourceKind="aggregate_api"`、`sourceId` 和 `upstreamModel`。
- 当前“新增自定义模型”表单与批量路由弹窗都能选聚合 API，但上游模型名仍手工填写；批量路由会把上游模型名强制设为本地 slug，不能表达发现项的独立上游模型名。
- 模型目录写入会替换该模型的完整路由集合；直接用完整 upsert 覆盖已有模型会误删既有路由、价格、权限组或其他元数据。网关对同一模型、同一聚合 API 只会选择一条优先路由。
- 上游 `/models` 响应仅可靠提供模型 ID 和可选显示名；不会可靠提供价格、上下文、能力或计费资格，不能凭空补全这些数据。
- 已保存聚合 API 被删除时，存储层会删除其关联的 V2 路由；新能力不需要新增表或迁移。

## Requirements

1. 发现结果中的模型必须保留其来源聚合 API 与上游模型 ID；快捷添加不得跨 API 误建路由。
2. 快捷添加必须把模型与路由作为一个一致操作处理：成功后本地目录可见对应模型，且该模型存在指向来源聚合 API 的显式路由，路由的 `upstreamModel` 等于发现结果的模型 ID。
3. 对已有本地模型，快捷添加不得覆盖价格、能力、可见性、启用状态、计费权限组、降级链或其他来源的路由。
4. 不得从发现结果猜测价格、上下文窗口、模型能力、计费权限或供应商元数据；这些字段保持明确的安全默认值或由管理员在现有编辑器中补充。
5. 写入必须复用当前 typed transport/RPC 和模型目录运行时同步链路，并同时支持桌面与 Web/service-mode。

## Key Decisions

- 快捷入口采用预填确认弹窗：从发现项带入本地模型标识、显示名、来源聚合 API 和上游模型 ID；用户确认后才写入。
- 服务端以发现项的模型 ID 和本地模型 `slug` 进行大小写不敏感匹配。若本地目录已有该模型，不得创建第二个本地模型；确认操作只会合并该模型的聚合 API 路由。
- 若本地目录不存在该模型，确认操作创建一个最小自定义模型，并写入发现来源的聚合 API 路由。
- 若已有模型已配置同一聚合 API 的路由但 upstream model 不同，确认操作更新该路由的 upstream model；保留该路由的 ID、启用状态、优先级和权重，不新增第二条同源路由。

## Candidate Approach

- 从现有发现弹窗内的每个模型结果进入，因其已持有稳定 `(apiId, upstreamModel)` 上下文，避免在模型管理页重新发现或依赖临时全局缓存。
- 新增面向该意图的原子服务端操作，而不是前端读出完整模型再普通 upsert：服务端可在单事务内“创建最小自定义模型或保留已有模型元数据，并合并/更新该 API 的一条路由”。
- 新模型的初始元数据应标记为未核实、价格缺失且不加入计费权限组；管理员仍可从既有模型编辑器完善详情。

## Out of Scope

- 自动推断或抓取价格、上下文、能力、计费权限、供应商说明。
- 改变上游发现的只读/瞬时数据策略，或把发现结果持久化为模型目录缓存。
- 改变网关的请求协议、候选选择、失败切换或聚合 API 鉴权语义。

## Acceptance Criteria

- [ ] 从某个发现项打开预填确认弹窗；确认后落库路由准确关联该发现项的聚合 API ID 和上游模型 ID。
- [ ] 本地目录已有同名模型时不创建第二个模型；除目标聚合 API 路由外的模型元数据和路由保持不变。
- [ ] 已有同源路由的 upstream model 被更新，原路由 ID、启用状态、优先级和权重保持不变；不会新增同源重复路由。
- [ ] 新模型不携带未经发现接口证明的价格、能力或计费归属。
- [ ] 成功后模型管理数据与运行时网关目录刷新；数据库写入失败时不留下模型或路由的半完成状态。
- [ ] 桌面与 Web/service-mode 走同一 typed command/RPC 合同。
