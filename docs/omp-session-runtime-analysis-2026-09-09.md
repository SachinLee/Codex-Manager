## 1. 结论摘要

这次会话耗时过长，**不能简单归因于 OMP 底层模型慢**。主要原因是以下因素叠加：

1. 任务本身是高风险、跨多个模块的 Rust 网关改造，范围明显超过普通小修复。
2. OMP 启用了规划、实现、质量检查、独立审查等多代理流程，编排链路过重。
3. 两个实现子代理长时间读取和分析，但没有产生代码修改，随后被主代理取消。
4. 主代理反复使用 `hub wait`、`hub jobs` 和 `hub list` 等操作等待或轮询子代理。
5. 主代理使用 `gpt-5.6-terra:xhigh`，且上下文持续膨胀，导致单轮推理成本和延迟增加。
6. 会话中出现 22 次工具错误，造成路径修正、重新读取和额外推理。
7. 任务后期又扩大到模型配置、RPC/UI 检查、构建和打包问题，导致任务边界继续扩大。

**总体判断：**

> 主要问题是“复杂任务 + 过重的 OMP 多代理工作流 + 子代理缺乏无进展终止机制”，其次才是模型推理等级和上下文规模。普通 Codex 或 Pi 看起来更快，主要是因为通常采用单代理、少门禁、少等待的直接执行模式。

## 5. OMP 配置对耗时的影响

分析的配置文件为：

```text
C:\Users\shuan\.omp\agent\config.yml
```

其中对性能影响较大的配置包括：

```yaml
default: codex-manager/gpt-5.6-terra:xhigh

task:
  maxRecursionDepth: 1
  maxConcurrency: 4

compaction:
  thresholdTokens: 230000
  keepRecentTokens: 16000
```

### 5.1 默认使用 `xhigh`

主代理默认使用 `gpt-5.6-terra:xhigh`。这适合架构设计和高风险审查，但不适合每一次：

- 文件读取；
- 状态检查；
- 路径修正；
- 小范围工具调用；
- 等待子代理返回。

建议把普通开发任务的默认等级降低到 `high`，只在架构设计、根因分析和最终审查阶段使用 `xhigh`。

### 5.2 上下文明显膨胀

会话中至少发生了两次上下文压缩：

```text
约 250k token → 约 51k token
约 259k token → 约 51k token
```

后期主代理每次输入平均约 7.6 万 token，而前期约 1.7 万 token。上下文变大以后，每次新的工具调用都会带来更高的模型处理成本和更高的延迟。

### 5.3 并发配置没有转化为有效吞吐

虽然 `maxConcurrency` 为 4，但这个任务存在：

- 同一代码文件的写入竞争风险；
- 用户要求测试串行运行，避免内存占用；
- 实际只能有一个主要 writer；
- 其他代理主要处于等待或审查状态。

因此，4 路并发没有显著加速，反而增加了任务管理成本。

## 8. 根因排序

### 第一：多代理编排过重

这个任务同时使用了规划、实现、质量检查和独立审查代理，且实现代理出现了长时间无产出。对于一个已有明确根因的修复任务，这种编排明显过重。

### 第二：子代理缺少无进展自动终止

子代理长时间只读取、不编辑，也没有及时被自动取消。主代理只能通过人工式消息和等待进行干预。

### 第三：主代理进行了重复轮询

虽然 hub 提示支持自动交付，但主代理仍然频繁检查状态。这是最明显的可避免时间浪费之一。

### 第四：默认推理等级过高

`xhigh` 被用于大量常规操作，增加了每轮响应成本。

### 第五：任务边界持续扩大

代码修复任务后来扩展到：

- OMP 配置；
- 模型目录；
- RPC/UI 检查；
- release build；
- 用户打包错误修复。

这些内容应该拆成独立任务或独立会话。

### 第六：路径和工具错误

22 次工具错误造成了额外返工，但它们不是最主要原因。

## 9. 建议的 OMP 使用方式

### 9.1 普通开发任务

建议采用：

```text
单主代理
→ 定位问题
→ 直接修改
→ 运行窄测试
→ 修复
→ 汇报
```

不要默认启动完整的规划、实现、检查、审查链路。

### 9.2 复杂高风险任务

可以保留 OMP 多代理，但建议简化为：

```text
主代理直接实现
→ 测试通过后派一个 review agent
→ 根据审查结果修复
→ 结束
```

不建议默认采用：

```text
planner → implementer → checker → reviewer
```

### 9.3 子代理 watchdog

建议增加以下硬规则：

```text
10～15 分钟没有文件变化或明确进度：
1. 要求立即回报状态；
2. 如果不能说明具体阻塞，自动取消；
3. 不自动重复派出相似代理；
4. 由主代理接管或结束任务。
```

### 9.4 限制等待

- 优先使用自动完成通知；
- 不要每分钟轮询 `hub jobs`；
- 单次等待设置合理上限；
- 子代理完成后立即结束该阶段；
- 每个阶段设置硬超时；
- 一个会话只处理一个明确目标。

### 9.5 调整推理等级

可考虑：

```yaml
default: codex-manager/gpt-5.6-terra:high
```

把 `xhigh` 限制在：

- 复杂架构设计；
- 关键根因分析；
- 高风险代码最终审查。

## 11. 最终结论

本次 5 小时以上的运行时间主要由以下组合造成：

```text
复杂网关任务
+ 过重的多代理流程
+ 两个实现代理长时间无产出
+ 反复 hub 等待和状态轮询
+ xhigh 推理
+ 上下文膨胀
+ 工具错误返工
+ 任务范围后期扩大
```

因此：

- 不是单纯 Rust 测试慢；
- 不是单纯模型推理慢；
- 不能简单说是 OMP 底层故障；
- 当前 OMP 多代理工作流确实存在明显的等待和失控风险；
- 对于追求完成速度的普通开发任务，单代理 Pi/Codex 模式通常更合适；
- 对于需要规划、审查、留痕和质量门禁的高风险任务，OMP 仍然有价值，但必须限制代理数量、等待时间和任务范围。
